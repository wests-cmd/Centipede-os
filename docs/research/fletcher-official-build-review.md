## What to carry into Kingdom and Centipede

1. **One orchestrator with specialized workers:** keep Kingdom authoritative; separate perception, speech and inference placement. A host model list is not proof of readiness. Track warm/loading/unavailable states and actual worker receipts.
2. **Measure the entire request:** microphone end → transcript → queue → model first token/completion → spoken playback. A fast model step does not mean fast speech. Test cold-start, timeout, fallback and cancellation.
3. **Use deterministic tools when sufficient:** known device commands and saved/rule answers can avoid inference. Camera text remains untrusted; model observations cannot grant device-control permission. Require actual state confirmation and bounded retries for physical actions.
4. **Perception is more than capture:** expose source, calibration, confidence and active status; test lighting and coordinate mapping before adding gestures. Keep keyboard/mouse/text paths. Gesture and camera support should be optional adapters, not mandatory dependencies.
5. **Shared memory needs evidence:** portable project-scoped notes and retrieval are useful; transcript ingestion, source provenance and correct retrieval must be tested. Nothing here proves training or a general autonomous coding worker.
6. **Hardware change requires separate acceptance:** storage cloning needs source-free reboot proof; a camera swap needs before/after tracking tests; a power LED or recognized device is not a passed application test. Do not copy this creator’s wiring or format the owner’s devices from a video.

## Repository priorities

See [source-backed implementation gaps and independent tests](jarvis-series-implementation-gaps.md). Current Centipede has explicit capture/preview, safer voice confirmation and honest inference availability. Still open: real vision/STT providers, durable project memory/outbox and jobs, transport-aware controls, measured routing/fallback, optional calibrated gestures, and exact-source graphical/headless installer proof. These are planned implementation gates, not changes claimed delivered by this research commit.
